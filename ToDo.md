## 1. Goals

1. **One model, many formats.** Parse PE and ELF uniformly behind a common interface, exposing shared concepts (sections, symbols, imports/exports, entry point, architecture) plus format-specific detail. Correctly distinguish executables vs. shared libraries (exe/dll vs. so).
2. **Five core views**, each format-aware:
   - Headers / summary (PE COFF + optional header; ELF header + program headers)
   - Sections (and ELF segments)
   - Imports / Exports (PE import/export tables; ELF dynamic symbols + needed libraries)
   - Raw bytes (hex/ASCII, with navigation to file offsets / RVAs)
   - Disassembly (Capstone) and **Decompilation** (pseudo-C)
3. **Live target inspection.** Open static files or attach read-only to a running process, starting with Win64 PE modules and Linux x64 ELF modules. Show process/module/thread/handle-style inventory, VMMap-style memory regions, live-memory hex/disassembly, and clear permission/staleness failures.
4. **Security posture reporting.** Surface BinSkim-style executable hardening facts: mitigation flags, debug/repro metadata, signing/certificate state, loader protections, section permissions, and suspicious configuration. Keep this as factual reporting first; policy scoring can come later.
5. **Production-quality code.** Consistent style, real error handling, no dead/duplicate paths, tests, and CI.

> **Testing is mandatory and gating.** Every feature — current and new — must have unit tests.
> A change (feature, refactor, or tech-debt fix) is **not complete** until the full unit-test
> suite builds and passes (`ctest` green). GoogleTest is the framework; tests live in `tests/`.
> No exceptions: code without passing tests is treated as unfinished.

## 2. Key decisions & open questions

Resolve these before the phases they gate; defaults are the recommended path.

- **D1 — Decompiler backend (resolved behind `IDecompiler`).** Implemented backends:
  - *Ghidra headless* (`GhidraDecompiler` via `analyzeHeadless` + `PeelfDecompile.java`) — primary default when Ghidra is configured/discovered; persistent project reuse is implemented in `WU-02`.
  - *In-tree Structured Pseudo-C* (`StructuredPseudoCDecompiler` + `AnnotatedCodeDecompiler`) — zero-dependency CFG/structured-control-flow decompiler over Capstone; automatic fallback when external decompilers are unavailable.
  - *RetDec* (`RetDecDecompiler` CLI subprocess) — optional LLVM-based external backend.
  - *Binary Ninja* (`BinaryNinjaDecompiler` via `bn_decompile.py` Python subprocess bridge) — optional backend for installed BN licenses without linking proprietary SDK binaries.
- **D2 — GUI scope.** Stay with Dear ImGui + Vulkan (current stack) vs. simplify the renderer. **Default: keep ImGui**, but harden the Vulkan layer (TD-7, TD-13) and pin ImGui (TD-10).
- **D3 — Platform priority.** **Default: Windows (MSVC) is primary** (matches current dev box), Linux/Clang kept green in CI.
- **D4 — Min toolchains.** C++23 requires VS 2022 ≥ 17.6 / Clang 18 + libstdc++ 13. Confirm we can require these.
- **D5 — Live-process scope.** Local process enumeration, attach/detach, command-line executable path resolution (`argv[0]`, `cwd`, `PATH`), VMMap-style region & module exploration, ASLR-rebased PE/ELF/PDB symbol & static metadata hydration, process/thread pause/resume (`ScopedProcessPause` RAII) + multi-arch register contexts, highlighted stack unwinding, TLS inspection, endian-aware heap/memory search, PEB/TEB + Linux runtime blocks, and VEH/SEH/unwind/signal/`atexit` handlers are implemented behind `IProcessBackend` / `IProcessSession`. **Live-process attach is strictly read-only** (`IProcessSession::is_read_only() == true`; Linux uses `O_RDONLY` `/proc/<pid>/mem` + `process_vm_readv`; Windows uses `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ` / `PROCESS_QUERY_LIMITED_INFORMATION` and never requests write/operation access). Active debugging (`IDebugSession`) is isolated into opt-in `WU-15`.
- **D6 — Security reporting stance.** Start with transparent facts and rule IDs inspired by BinSkim output, not pass/fail compliance claims. Each finding must cite parsed evidence (header flag, directory entry, section characteristic, certificate/debug record, or live mapping property).
- **D7 — Byte editing / patching stance.** **Static on-disk files** support explicit, transactional staged patching in `PagedBinaryImage` (inline Hex edits, Shellcode scratchpad, Patch Set undo/redo) and require explicit `Save Patched As...` (never overwriting the input file by default). **Live attached processes are strictly read-only**—all byte-mutation UI and model entry points reject live sessions so inspected processes are never modified. Capstone is the disassembly engine only; assembly→bytes generation uses `IAssemblerProvider` (`peelf::asmtk` for x86/x64 and `llvm-mc` for multi-arch in `WU-11`).

## 14. Suggested sequencing

1. **Phase 0** (debt + foundations) — unblocks all.
2. **Phase 1** (unified model) — the spine everything hangs off.
3. **Phases 2 → 3 → 4** (sections/bytes → imports/exports → disasm) — incremental, each demo-able.
4. **Phase 6** rendering hardening can run in parallel once Phase 0 lands.
5. **Phase 5** (decompile) after Phase 4 and the D1 decision.
6. **Phase 7** (tests/CI) starts during Phase 1 (parsers are the highest-value test target) and continues throughout.
